# Courier franchise bulk receiving: evidence and workable design

## Scope and evidence limits

Research below covers **34 distinct registrable domains** (subdomains are not counted separately). Sources were searched and their accessible extracted page/PDF text read; no authenticated courier account, production endpoint, or partner contract was tested. Documentation availability does not establish present commercial availability or permission for a franchise to post internal hub events. Some pages are dynamic, old, or lightly extractable: limitations are identified below. These findings establish neither an implemented integration nor universal provider support.

**Labels:** API = technical integration documentation; Standard = primary specification/guideline; Operations/help = operational/customer instructions; Marketing = capability or commercial description, not an executable API contract.

Supplemental [webhook reference](https://delhivery-express-api-doc.readme.io/reference/tracking-via-push-api-webhook-1) describes onboarding a client endpoint, sharing authorization/header details and testing with live waybills; do not infer a standard HMAC scheme. It does not publish request schemas, bag-seal APIs or a universal OTP requirement.

3. **xpressbees.com — Marketing/franchise terms, primary.** [Franchise partner](https://www.xpressbees.com/partner/franchise-partner) distinguishes a booking counter from a parcel-delivery operation; delivery franchises serve assigned pincodes, need shipment storage and source riders. Verify current onboarding and production access before relying on historical examples; no bag-receipt API is established here.

Reverse-pickup OTP evidence must not be generalized into a forward-delivery or bulk-receipt OTP contract.

6. **bluedart.com — Marketing/product integration overview, primary.** [Business integrations](https://www.bluedart.com/business-integrations) describes ShopTrack as an API and registered-customer tools for downloading tracking/status data and reports. [Open Box Inspection](https://www.amazon.in/gp/help/customer/display.html?nodeId=GNHMSYW5BTFBTMEW) describes inspection of eligible products at delivery. A login OTP and a delivery OTP are different purposes; this evidence does not establish one reusable recipient OTP for all parcels.

9. **flipkart.com — Customer terms, primary.** [Open Box Delivery terms](https://www.flipkart.com/pages/obd-tnc) describe OTP arrival when the product is out for delivery, a separate phone-number check to initiate OBD, inspection and rejection for specified problems. Follow the shipment’s current acceptance sequence; a phone suffix check is not evidence that a delivery OTP can be bypassed or bulk-reused.

[Delhivery SPS](https://docs.clickpost.ai/docs/delhivery-sps) documents an account OTP-verification configuration. A parent bag ID and its declared child pieces form an aggregation assertion—not physical proof that every child was observed at receipt. 21. **github.io — Maintainer OCR documentation; counted once despite two hosts.** [Tesseract image-quality guide](https://tesseract-ocr.github.io/tessdoc/ImproveQuality.html) discusses rescaling, binarization, noise, deskewing, borders and segmentation. Perspective correction can prepare skewed labels for barcode/OCR processing; it does not infer the destination.

24. **owasp.org — Security guidance, primary.** [API1:2023 BOLA](https://owasp.org/API-Security/editions/2023/en/0xa1-broken-object-level-authorization/) requires authorization checks for each object accessed through an ID. Knowing an AWB—even a hard-to-guess one—is not authorization to retrieve its address, phone or POD.

25. **rfc-editor.org — Internet standard, primary.** [RFC 9421](https://www.rfc-editor.org/rfc/rfc9421.html) specifies HTTP message signatures/MACs over message components. It is an available standard for controlled integrations, not evidence that any named courier implements it.

26. **github.com — Platform webhook documentation, primary.** [Validating webhook deliveries](https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries) documents secret-based verification and the `X-Hub-Signature-256` header. 27. **stripe.com — Platform event documentation, primary.** [How events work](https://docs.stripe.com/events/how-events-work) describes asynchronous state-change events and thin versus snapshot formats. It illustrates the distinction between event delivery and business processing; Stripe’s behavior must not be asserted as a courier guarantee.

28. **aftership.com — Tracking API documentation, primary for this aggregator.** [Webhook signature](https://www.aftership.com/docs/tracking/webhook/webhook-signature) specifies `aftership-hmac-sha256`, a base64 HMAC-SHA256 of the request body using the account webhook secret. 29. **easypost.com — API documentation, primary.** [ScanForm](https://docs.easypost.com/docs/scan-form) documents one carrier scan marking included tracking codes accepted for shipment, with same-origin/account and other constraints. 30. **goshippo.com — API documentation, primary.** [Manifests and SCAN forms](https://docs.goshippo.com/manifests-and-pickups/manifest-and-scan-forms) documents daily close-outs and shared origin/date/carrier-account constraints. It demonstrates batch carrier acceptance where supported, not blanket permission to batch-close Indian delivery OTPs.

31. **nist.gov — Authentication standard/guidance, primary.** [Authenticator requirements](https://pages.nist.gov/800-63-4/sp800-63b/authenticators/) distinguishes out-of-band secrets from authenticator-generated OTPs and ties them to possession proof. A phone challenge is not, by itself, evidence of parcel contents, count or physical handover; NIST is not a courier delivery policy.

32. **rabbitmq.com — Messaging technical documentation, primary.** [Reliability guide](https://www.rabbitmq.com/docs/reliability) explains distributed failure modes and shared publisher/consumer responsibility for safe delivery. 33. **meity.gov.in — Government legal reference, extraction limited.** [Digital Personal Data Protection Act, 2023 entry](https://www.meity.gov.in/content/digital-personal-data-protection-act-2023) identifies the official Act entry, but accessible extracted text did not expose the Act’s substantive provisions. 34. **delvexpress.com — Marketing/operations description, primary company claim.** [Network service](https://delvexpress.com/services/network) advertises bulk handover by API/dashboard/file/manifest and a sequence of manifest receipt, linehaul bag scan, hub piece scan/sort, rider out-scan and doorstep ePOD/OTP/COD. This is unusually relevant to separating bag and piece events, but not a published API contract or independent verification; **Delv Express is not Delhivery**.

## Key conclusions

- **Three different “manifests”:** shipment creation/manifestation, a bag-to-piece contents list, and a carrier daily close-out/SCAN form. An endpoint supporting one does not establish support for the others (1, 15–18, 29–30).
- **Bag receipt is not verified piece receipt.** A sealed bag may be accepted into custody while its contents remain declared/unverified. A matching total alone cannot detect one missing piece offset by an unexpected piece (7, 15–16).
- **A scan, electronic inward receipt, carrier acceptance and final POD are different evidence objects.** Preserve what was actually observed; do not convert an internal scan into a carrier-confirmed state without an authorized integration (1, 14, 29).
- **No reviewed source establishes one recipient OTP universally replacing every parcel’s delivery OTP.** Account authentication proves control of a channel/session. A carrier delivery challenge applies to its documented order/shipment transaction. Several boxes can also belong to one multi-piece shipment: do not invent a universal “one code per physical box” rule (1, 5, 8–9, 11, 31).

## Recommended receiving workflow — proposed design, not a provider promise

1. **Contract and capability gate.** For each provider/account obtain franchise SOP, inward authority, assigned pincodes, manifest format, bag/seal identifiers, discrepancy deadlines, liability terms, OTP requirements and POD access. Record each capability as `unverified`, `contract-approved`, `sandbox-tested` or `production-enabled`. No unsupported provider should appear as “integrated.”
2. **Pre-advice.** Import an authorized API/file/manual manifest; retain its source, version and digest. Namespace identities by provider/account plus AWB/piece ID. Store expected bags, declared pieces, parent–child mapping and destination depot when supplied. An absent manifest means “unadvised receipt,” not zero expected parcels.
3. **Dock custody.** Scan trip/manifest and bag IDs; record sender, receiver, location/time, seal ID and intact/broken/missing status. Photograph exceptions under a controlled retention policy. Compare **actual bags with expected bags**. Give a provisional custody receipt stating “contents unverified”; quarantine tampering or wrong-destination bags according to SOP.
4. **Open and scan.** Open authorized bags under a named operator, witness where policy requires. Scan each piece once into that receiving session. Preserve duplicate scan attempts separately without inflating received count. Log unreadable labels, damaged pieces and unmanifested arrivals. A bag-only path may remain valid for approved closed-bag transfers, but must retain its unverified-content status.
5. **Set reconciliation.** With expected unique identities `E` and observed unique identities `R`, calculate `missing = E − R`, `unexpected = R − E`, and `matched = E ∩ R`. Track duplicate attempts and damaged parcels separately; compare piece identities, not merely totals. Example: 100 expected and 100 scanned can still contain one missing and one extra.
6. **Close the receipt.** Issue an electronic inward receipt containing receipt/manifest version, bag/seal findings, expected and observed piece counts, exception identities, operator/time and sender acknowledgment or refusal. Explicitly state accepted custody versus accepted condition/count. Corrections append a new version and reason, never silently overwrite evidence.
7. **Sort and dispatch.** Assign validated pieces to a deterministic destination and scan into a named bin/cage/bag. At closure reconcile planned versus packed identities, attach the outbound parent mapping and seal record, and scan handover to the authorized next custodian. Franchise inward receipt must not become “delivered to customer.”
8. **Recipient collection/delivery.** Verify authority for collection and show the exact parcel list. A locally issued recipient challenge may authorize that explicitly enumerated local handover, but cannot substitute for carrier-required delivery challenges. Complete each carrier’s transaction-bound challenge in its authorized workflow; preserve individual outcomes and support partial handover/refusal. Never solicit login/banking OTPs or persist OTP plaintext in logs, OCR images or receipts.
9. **Offline resilience.** Queue locally identified scan events with device/session sequence and observation time; mark them pending sync. Do not claim remote confirmation or OTP verification offline unless the specific provider expressly supports it. Sync with duplicate-safe processing and discrepancy review.

## Non-generative OCR and deterministic destination routing

**Preferred chain:** barcode decode → authorized AWB/manifest lookup → exact routing rules; OCR is a fallback for damaged/unreadable labels, not a destination guesser.

- Capture a single label at controlled focus/lighting; crop and correct perspective/rotation with OpenCV (23). Decode approved symbologies locally with ZXing-compatible software (22). Multiple plausible AWBs go to review.
- Use **Tesseract** or a pinned conventional **PP-OCR text detection/recognition model**, explicitly excluding generative VLM, chat, document “reasoning” and address completion features (21). Retain field boxes, recognized text, confidence, engine/model version and necessary source crop. These are learned recognizers and can misread; “non-generative” does not mean infallible or automatically bit-for-bit deterministic across hardware.
- Extract AWB and **destination-region** pincode using provider-specific label templates; do not select the first six-digit string, since labels may contain sender/return pincodes. Preserve leading zeros in identifiers. Normalize only documented separators/case; do not silently rewrite ambiguous O/0 or I/1 characters.
- Validate identifiers using documented format/check digit **where available**, then exact-match authorized manifest data. Never invent a courier checksum. A syntactically valid six-digit pincode alone is not proof of destination or provider serviceability.
- Route using a versioned table such as `(provider, account, destination_pincode, service, effective_date) → depot/route/bin`, constrained by that franchise’s assigned coverage (3). Add exact locality/beat keys only from approved reference data. Precedence: authorized destination record → validated destination label fallback under policy → manual review. Contradictions must block automatic routing rather than silently favoring OCR.
- Require exactly one active rule. Missing rule, competing rules, label/manifest conflict, low confidence, unserviceable destination or changed label sends the parcel to an exception bin. Fuzzy matching may offer suggestions to staff but must not commit a destination.
- Store rule version, input evidence, selected destination and override actor/reason for replay. Evaluate on representative label images and measure **false automatic routing**, unreadable rate and review rate; tune confidence thresholds from this evidence, not arbitrary claims such as “99% accuracy.” Test same-count/wrong-identity cases, return-address confusion, duplicate labels, multi-piece orders and outdated route assignments.

## Integrations, automation and privacy controls

- Implement a provider/account capability matrix: inward pre-advice, internal receipt write, public tracking read, webhook, POD, OTP completion and bag/seal operations are separate permissions. Documentation of booking/tracking does not authorize franchise inward writes. For unsupported operations offer explicit manual receipt/file import, not a simulated successful API call.
- Accept webhooks only over HTTPS; apply the **actual provider’s** documented auth/signature contract. Never invent a shared courier header. Use raw bytes for body-signature verification where specified; retain enough metadata for audit but redact secrets/OTP/PII. HMAC without freshness does not stop legitimate-message replay (25–28).
- Persist validated events durably before acknowledging within the provider’s response window; process asynchronously. Use provider event IDs where available, otherwise a carefully defined account/AWB/event/time/payload identity. Preserve distinct legitimate scans, accept duplicates idempotently and do not assume delivery order or universal retry behavior. Unknown status codes go to mapping review rather than being discarded. Poll/backfill only if authorized, rate-limited and documented; keep stale/unknown states visible (1, 13, 32).
- Maintain separate local custody state and provider-reported shipment state, with event time and received time. A webhook is a provider assertion, not a substitute for local physical reconciliation. Keep raw events access-controlled and normalize using versioned provider mappings.
- Enforce tenant, branch, role and parcel-level access. Do not make full tracking records public merely because someone knows an AWB (24). Public tracking should disclose minimal status; addresses, full phones, label photos, signatures, ID numbers, rider location and POD require authorization.
- Use expiring scoped receipt/POD links, private storage, encryption and controlled exports; avoid names/phones in URLs, analytics, browser logs or unrestricted QR content. QR receipts should resolve an opaque reference subject to access checks.
- Prefer on-premise/local OCR; prohibit arbitrary uploads of parcel labels to public decoder/OCR demos. Specify processor agreements and retention schedules by evidence type. Separate operational dispute retention from short-lived OCR intermediates; deletion/legal-hold behavior must be tested. Do not claim DPDP compliance from this architectural checklist alone (33).

## Practical pilot and acceptance gate

Start with one authorized provider and depot, barcode-only receipt plus approved manifest CSV, explicit bag/seal checks, piece-set reconciliation and exception receipts. Add conventional OCR only after evaluating real damaged labels; add tracking/POD adapters only after account-specific approval and tests. Before enabling any provider write operation, test duplicate/out-of-order callbacks, invalid signatures, wrong-account AWBs, missing/extra pieces, broken seals, partial collections, OTP expiry/refusal, offline sync and route-table changes. Ship only when unsupported cases fail visibly, every automatic route is explainable, and reconciliation can be reproduced from retained evidence.
